# 4. Implementation Review

## 4.1 `Main.qml`

Current implementation:

```qml
import QtQuick

Rectangle {
    id: root
    width: Screen.width
    height: Screen.height
    color: state.bgColor

    readonly property real s: Screen.height / 768

    ThemeState {
        id: state
        s: root.s
    }
}
```

### Assessment

**Status: PASS**

The implementation is intentionally minimal and matches the Stage 1.1 scope.

Positive aspects:

- root is a `Rectangle`;
- background is delegated to `ThemeState`;
- scale factor is calculated exactly as required;
- `ThemeState` receives the scale from the visual root;
- no unnecessary Stage 1.2 functionality was introduced.

The following architectural flow is clear:

```text
Screen.height
      │
      ▼
Main.qml
      │
      │ s = Screen.height / 768
      ▼
ThemeState
```

This is preferable to calculating screen geometry independently in multiple components.

### Finding

No blocking issue.

# 4.2 Scale Ownership

Current implementation:

```qml
readonly property real s: Screen.height / 768
```

inside `Main.qml`.

Then:

```qml
ThemeState {
    id: state
    s: root.s
}
```

### Assessment

**Status: PASS**

The Stage 1.1 implementation correctly follows the implementation plan decision:

> Scale is calculated only in the visual root `Main.qml`.

This creates a clear ownership model:

```text
Main.qml
    owns screen-derived scale

ThemeState.qml
    receives scale

Components
    receive scale from composition/state
```

This is a sound architectural decision.

It prevents multiple components from independently reading screen geometry and calculating potentially divergent scale values.

# 4.3 `ThemeState.qml`

Current implementation:

```qml
import QtQuick

QtObject {
    id: themeState

    property real s: 1

    readonly property bool isPreview: typeof sddm === "undefined" || sddm.hostName === undefined

    readonly property color bgColor: {
        if (!isPreview && typeof config !== "undefined" && config.bgColor)
            return config.bgColor
        return "#000000"
    }
}
```

## Assessment

**Status: PASS**

The implementation provides graceful degradation when the QML environment is not running inside a real SDDM greeter.

The following scenario is handled:

```text
Preview environment
       │
       ▼
sddm unavailable
       │
       ▼
isPreview = true
       │
       ▼
config access avoided
       │
       ▼
bgColor = #000000
```

This is appropriate for early-stage theme development.

### Positive aspects

- `sddm` is guarded using `typeof`;
- `config` is guarded;
- background has a deterministic fallback;
- preview mode does not depend on a live SDDM environment.

### Minor concern

The current preview detection:

```qml
typeof sddm === "undefined" || sddm.hostName === undefined
```

couples preview detection to the existence of `hostName`.

This is acceptable for the current stage, but future SDDM integration should avoid assuming that `hostName` is the canonical capability check for the entire `sddm` object.

### Recommendation

No immediate change required.

When a permanent preview runner and SDDM mock are introduced, consider defining preview detection more explicitly.

Example future direction:

```text
explicit preview environment
        OR
mocked SDDM interface
        OR
capability-based checks
```

# 6. `validate.sh` Review

Current validation logic primarily checks for required files.

Conceptually:

```text
Required file exists?
        │
        ├── yes → continue
        │
        └── no → fail
```

Required files include:

```text
Main.qml
ThemeState.qml
translations.js
PROVENANCE.txt
metadata.desktop
theme.conf
```

## Finding: MINOR

### Severity

**MINOR**

### Problem

The script is named:

```text
validate.sh
```

but currently does not perform meaningful semantic validation.

It does not validate:

- QML syntax;
- QML imports;
- Qt6 compatibility;
- `MainScript` existence;
- `metadata.desktop` fields;
- `theme.conf` fields;
- SDDM theme structure;
- component import resolution.

Therefore:

```bash
./validate.sh
```

should currently be interpreted as:

> required project files exist

rather than:

> the theme is valid

### Example failure scenario

The following broken QML could still pass:

```qml
Rectangle {
    completely invalid syntax
}
```

provided that the file exists.

### Recommendation

Do not block Stage 1.1.

However, before MVP freeze, validation should become layered.

Recommended structure:

```text
validate.sh
│
├── File structure validation
│
├── metadata.desktop validation
│
├── theme.conf validation
│
├── QML syntax validation
│
└── optional runtime smoke validation
```

Possible future command flow:

```bash
./validate.sh
qmllint theme/onyx/Main.qml
qmllint theme/onyx/ThemeState.qml
```

As the project grows, validation should discover all QML files automatically.

# 7. Architecture Documentation Inconsistency

## Finding: MINOR

### Severity

**MINOR**

### Location

`docs/ARCHITECTURE.md`

### Problem

The architecture document describes scale ownership as:

```qml
// In ThemeState.qml
readonly property real s: Screen.height / 768
```

However, the actual implementation uses:

```qml
// Main.qml
readonly property real s: Screen.height / 768
```

and then:

```qml
ThemeState {
    s: root.s
}
```

The Stage 1.1 implementation plan explicitly states that the accepted architecture is:

> Scale is calculated only in visual root `Main.qml`.

Therefore the project currently has two conflicting architectural descriptions.

---

## Why this matters

This is not merely documentation cosmetics.

Future agents may follow `ARCHITECTURE.md` instead of the Stage 1.1 implementation plan.

That could lead to:

```text
Main.qml calculates s
        │
        ▼
ThemeState calculates s again
        │
        ▼
Components calculate s independently
```

Eventually producing fragmented scale ownership.

The desired model should be:

```text
Screen geometry
      │
      ▼
Main.qml
      │
      ▼
Single scale value
      │
      ├───────────────┐
      ▼               ▼
ThemeState       Components
```

---

## Required recommendation

Update `docs/ARCHITECTURE.md` before or during Stage 1.2.

Recommended wording:

```markdown
### Scaling

The scale factor is calculated only by the visual root:

```qml
readonly property real s: Screen.height / 768
```

`Main.qml` owns the screen-derived scale.

`ThemeState` receives `s` from the root and exposes it as global theme state.

Visual components receive the scale through composition/state and must not independently calculate screen scale.
```

This does not mean CI failed.

It means:

```text

    ≠

```

Possible explanations include:

1. CI ran only against the PR head branch.
2. The workflow triggers only on `pull_request`.
3. CI completed before squash merge.
